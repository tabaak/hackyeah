Дата фиксации: 3 октября 2026. Источник: сообщения Виктора от 2–3 октября, переданные пользователем. Это документация договорённостей и предложенных контрактов, а не описание уже реализованного API.

## Пользовательский поток

1. Вход; в первом сообщении указан Google Sign In.
2. Ручное заполнение минимального профиля организации.
3. Необязательная загрузка документов организации для более подробного анализа.
4. Dashboard: общая сводка, аналитика, Live Feed и карточки incidents.
5. Отдельные вкладки Live Feed, Analytics, Documents; профиль и уведомления в верхней панели.
6. Live Feed собирает упоминания организации из Twitter/X, Google News и Facebook.
7. Incidents объединяет потенциальные угрозы и проверяемые утверждения; система готовит черновик ответа, затем человек проверяет и утверждает его.
8. Демо включает имитацию попытки утечки секретов из документов и её блокировку.

Ограничение интерпретации: негативная тональность не доказывает дезинформацию; сигналы координации не доказывают существование ботофермы. Ответ может признать проблему или недостаточность доказательств.

## Общие соглашения

- Базовый префикс: `/api/v1` (в таблицах опущен).
- Защищённые пользовательские запросы: `Authorization: Bearer <supabase_jwt_token>`.
- Роль (`analyst` / `compliance`) и организация определяются сервером.
- Все парсеры сохраняют данные в единую таблицу `mentions`, `platform = facebook | twitter | gnews`.
- Документы: `processing | ready | failed`; классификация: `public | internal | confidential | restricted`.
- Публикация в MVP идёт в симулированный outbox.
- Webhook провайдера имеет собственную проверку подлинности; пользовательский JWT не заменяет её.

## 1. Авторизация и профиль

Ответственные: Витя / Макс.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/auth/login` | Вход; альтернатива — непосредственно Supabase Auth SDK на frontend |
| GET | `/me` | Пользователь, роль, организация |
| PUT | `/me` | Обновление пользовательского профиля; присутствует в первом списке |
| GET | `/organization` | Название, aliases, сектор bank/defence, мониторинговые темы |
| PUT или PATCH | `/organization` | Ручное заполнение и обновление организации и поисковых ключей |

Открыто: Google Sign In в первом описании против email/password во втором. Выбрать один основной сценарий входа. `/me` и `/organization` описывают разные сущности.

## 5. Incidents и AI

Ответственные: Саня — LLM; Витя — сохранение и API.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/incidents` | Фильтры severity, status (open/review/resolved), is_injection_attempt |
| GET | `/incidents/{id}` | Кластер, всплеск, claims, доказательства, черновик, Disclosure Check |
| POST | `/incidents/{id}/generate-counter-argument` | Генерация или перегенерация проверенного ответа по доказательствам |
| PATCH | `/incidents/{id}/draft` | Ручная правка, повторная проверка раскрытия, снятие старого подтверждения |
| POST | `/incidents/{id}/request-approval` | Запрос подтверждения; confidential требует compliance |
| POST | `/incidents/{id}/approve` | Подтверждение человеком конкретной версии и хэша |
| POST | `/incidents/{id}/publish` | Проверка подтверждения и запись в outbox |
| POST | `/incidents/{id}/resolve` | Закрытие с причиной; в обсуждении также предложено имя dismiss |

Несмотря на историческое имя `generate-counter-argument`, система не обязана опровергать публикацию. Вердикты: подтверждается, противоречит документам, недостаточно данных, мнение.

## Дополнительный KYC-план: что он добавляет

PDF сохранён целиком без изменений. Его приоритеты: F0 → F1 → F4 → F5 → F2 → F3.

| Фича | Содержание |
|---|---|
| F0 | Общий движок, Supabase, ingest Apify, классификация Jev, роутер public/confidential, audit log |
| F1 | Репутационный риск компании и связей глубины 1; отсев одноимённых компаний; факты, точные цитаты и детерминированный балл 0–10 |
| F2 | Мониторинг событий, пересчёт риска, алерты, replay |
| F3 | Проверка утверждений и ответ на скандал; в PDF это P1 |
| F4 | Policy navigator: сопоставление KYC-досье с пунктами политики; жёсткие запреты реализованы кодом |
| F5 | Бриф для руководства, вопросы по собранным данным, подпись аналитика, экспорт PDF |

Отдельные сущности PDF: entities, sources_raw, articles, findings, scores, policies, policy_clauses, client_files, assessments, memos, audit_log. Это не автоматическая замена схемы mentions/incidents.

## Маршрутизация моделей из обсуждения

- Два подключения: основное облачное для public; локальное для внутренних и конфиденциальных данных.
- Выбор делает сервер по меткам всего контекста, включая историю и производные ответы.
- При недоступности локальной модели закрытые задачи не переключаются в облако.
- Restricted остаётся недоступным агенту согласно clearance основного плана.
- Индексация закрытых документов и их эмбеддинги также должны оставаться в разрешённом периметре.
- На M4 Pro 48 ГБ уже есть Qwen3.8-27B MLX 4-bit и Uncensored MLX 6-bit. Bonsai 2 27B MLX 2-bit скачивается как кандидат для сравнения, не утверждён как замена.
- Сравнивать время полного валидного ответа, JSON, цитаты, вердикты и память на одинаковых примерах. Выбор модели ещё не подтверждён замерами.

## Расхождения, которые ещё не согласованы

1. Центр продукта: основной план и API — мониторинг и incidents; PDF — KYC, F1/F4/F5. Нельзя молча считать все функции обязательным MVP.
2. Источники: PDF предлагает Apify; команда распределила Facebook/Twitter-парсеры и Serper. Реализуемый способ доступа нужно явно закрепить.
3. Авторизация: Google OAuth или email/password.
4. Схемы данных: mentions/incidents против entities/findings/assessments. Общие сущности и миграции пока не определены.
5. API основного плана использует `/documents`, отдельные `/approvals` и `/dismiss`; присланный API — `/documents/upload`, incident-level `/approve`, `/resolve`. Нужен единый контракт до интеграции frontend.
6. PDF предусматривает demo offline, но облачный Supabase требует сети. Для настоящего offline-прогона нужные документы, политика и результаты должны быть доступны локально заранее.
7. Термин Jev в PDF остаётся неопределённым: модель, сервис или название шага.

## Предложения к реализации — ещё не согласованный API

- Долгие sync/генерации: `202 Accepted` с job_id; worker, идемпотентность и статусы queued/running/succeeded/failed.
- `GET /jobs/{id}` для прогресса; incident возвращает analysis_status.
- Журнал решений роутера и доступности локального провайдера для Control Console.
- Повторная проверка версии/хэша при публикации; модель не выбирает сама роль утверждающего.
- Черновик из прогона с confidential-контекстом сохраняет требование compliance даже при удалении секретной цифры из текста.

Эти предложения отделены от исходного списка команды, чтобы не выдавать их за утверждённые договорённости.
