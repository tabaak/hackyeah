Открытый вопрос к команде: что такое Jev — модель, сервис или человек?

Архитектура и маршрутизация моделей
Все пять фич работают на одном пайплайне. Где можно облако, а где только
локальная модель, решает роутер по метке данных, а не разработчик в коде
фичи.




поток данных · 2 зоны, роутер между ними

Верхняя зона работает с публичными статьями, нижняя — с данными клиента и
банка. Единственный путь между ними — через роутер, и факты переходят
вниз, а не досье вверх.

F0. Фундамент: общий движок
Без F0 не работает ни одна из пяти фич, поэтому первые три часа вся команда
на нём. Цель к 14:00: статья из Apify проходит Jev и сохраняется с причиной, а
роутер кодом отказывает в отправке конфиденциального в облако.

 1. Репозиторий. Monorepo: frontend (React + Vite), backend (FastAPI), worker .
      .env в .gitignore с первой минуты, .env.example без значений. Ключи:
     Supabase, облачный LLM, токен Apify.
 2. Supabase. Проект, расширение pgvector, приватный bucket, два пользователя:
      analyst и compliance . Таблицы:

           entities — компании и связанные лица;
           sources_raw — сырые результаты Apify;

           articles — нормализованные статьи;
           findings — факты с цитатами;

           scores — балл и его компоненты;

           policies , policy_clauses — политика банка по пунктам;
           client_files — KYC-досье;

           assessments — итог по клиенту;
           memos — брифы;

           audit_log — журнал.
 3. Локальная модель. Ollama на самом мощном ноутбуке команды, модель 7–
     8B с JSON-выводом. Замерить скорость на реальном промпте в первый час.
     Если медленно — локально оставить только то, что обязано быть локальным
     (F4 и конфиденциальные части F5).
 4. Роутер моделей. Одна функция llm.call(task, payload, labels) . Метка
     данных ( public / confidential ) выбирает эндпоинт. confidential → только
     локальная модель, иначе исключение. Каждый вызов пишется в audit_log :
     задача, модель, метка, время, стоимость.
 5. Ингест Apify. Выбрать 2–3 актора: новостной поиск, Google News, извлечение
     полного текста статьи. Запуск через API Apify (синхронный запуск с
     получением датасета — проверить в первый час), результат → sources_raw →
     нормализация в articles (url, title, text, published_at, source, lang).
     Дедупликация по URL и хэшу текста. Проверить баланс кредитов Apify до
     старта.
 6. Jev. Вход: статья + профиль сущности (название, страна, отрасль, ключевые
     люди). Выход JSON: relevant , entity_match ( same / different / unsure ),
      category , stage , confidence . Каскад: сначала локальная модель; если

      confidence ниже порога, повтор в облаке (статья публичная, это разрешено).
 7. Контракты. JSON для findings , score , assessment согласовать в первый

а не на глаз.


F1. Репутационный риск компании и её связей
F1 — главная фича демо. Она отвечает на вопрос «насколько рискованна
компания и её окружение» баллом 0–10 с аргументами, где каждый аргумент
ведёт к цитате.

Вход: название и страна, опционально LEI или номер KRS.

 1. Карточка сущности. Название, варианты написания, страна, отрасль.
     Идентификаторы из открытых реестров: GLEIF (LEI и материнские компании),
     для Польши — KRS (правление, владельцы). Доступ к обоим API проверить в
     первый час. Не работает — связи вводятся вручную.
 2. Связи. Материнская компания, дочерние, ключевые лица (руководство,
    бенефициары). В MVP глубина 1.
 3. Санкции и PEP. Скрининг по открытому датасету (OpenSanctions; лицензию
     проверить, бесплатен для некоммерческого использования). Точное
     совпадение — флаг. Нечёткое — «требует проверки», решает человек.
 4. Новости. Для каждой сущности: Apify → Jev → релевантные статьи.
 5. Извлечение фактов (облако, только публичные статьи): категория
    (коррупция, мошенничество, санкции, экология, трудовые права, суды,
     спорная продукция), стадия (обвинение, расследование, обвинительный акт,
     приговор или мировое соглашение, оправдание), дата, источник, точная
     цитата.
 6. Склейка событий. Десять статей об одном событии — одно событие.
     Перепечатки не считаются независимыми подтверждениями.
 7. Проверка цитат. Цитата должна дословно найтись в тексте статьи. Факт
     без найденной цитаты отбрасывается.
 8. Балл по матрице (раздел ниже) для компании и для каждой связи. Риск
     связей добавляет до 1 балла компании.
 9. Экран. Балл и полоса (low / medium / high), разложение по компонентам, под
    каждым — факты с цитатами и ссылками, связи с цветом риска, отдельно —
     отброшенные статьи об одноимённых компаниях.

Модели: облако для статей; локально, если связи пришли из внутреннего

Готово, когда: у демо-компании есть балл, минимум три факта с цитатами,

Не делаем: глубину связей больше 1, автоматическое распутывание сложных
структур владения.


F2. Мониторинг и защита репутации
F2 — это цепочка F1, запущенная по расписанию. Она следит за банком и его
клиентами и поднимает тревогу, когда новая публикация меняет картину
риска.

 1. Watch-list. Сам банк, клиенты из портфеля (синтетические), темы риска.
 2. Расписание. Worker раз в N минут запускает акторы Apify по watch-list.
    Частоту ограничить кредитами Apify; бюджет проверяется до запуска.
 3. Новое или старое. Jev → извлечение фактов → сравнение с известными
     событиями: новое событие или продолжение уже учтённого.
 4. Скорость. Публикации об одном событии группируются; число публикаций
     за окно времени — сигнал того, что история разгоняется.
 5. Пересчёт. Новое событие пересчитывает балл клиента. Алерт — при
     переходе полосы (например, medium → high) или при событии максимальной
     тяжести.
 6. Алерт. Карточка в ленте с причиной. Опционально Telegram, только шаблон:
     имя, новый балл, ссылка, без внутренних данных.
 7. Replay для демо. Заранее собранные статьи подаются в тот же пайплайн с
    ускорением. Помечены как demo.

Модели: Jev каскадом, извлечение — облако.

Готово, когда: статья из replay меняет балл клиента и создаёт алерт с
понятной причиной.

Не делаем: мониторинг всего интернета, живой опрос Apify во время показа.


F3. Ответ на текущий скандал
F3 нужен компании, у которой скандал прямо сейчас. Он разбирает
утверждения, находит, что их подтверждает и что опровергает, и готовит
контрпозицию. Это ядро прошлого плана v2, код переиспользуется.

 1. Вход. Событие из F2 или ссылка и текст публикации.
 2. Утверждения. До трёх конкретных проверяемых утверждений.
 3. Доказательства. Внешние публикации: подтверждают или опровергают,
     независимые или перепечатки. Внутренние документы компании — только
     через локальную модель.
 4. Вердикт по каждому утверждению: подтверждается, противоречит
     документам, недостаточно данных, мнение.
 5. Контраргументы только с доказательствами. Если опровержения нет,
     система так и пишет. Искать «аргументы против» ради баланса запрещено:
     это превращает инструмент в генератор оправданий.
 6. Черновик контрпозиции. Признать подтверждённое, уточнить масштаб,
     опровергнуть с цитатами то, что опровергается. Внутренние факты
     попадают в публичный текст только после подтверждения владельцем
     данных (роль compliance ).
 7. Утверждение человеком. Правка после подтверждения снимает его.

Модели: внешние статьи — облако; внутренние документы и черновик,
который на них опирается, — локально.

Готово, когда: одно событие даёт два утверждения с разными вердиктами и
черновик, где каждое утверждение со ссылкой.

Приоритет: P1. Делать только после работающих F1, F4, F5.


F4. Policy navigator
F4 сопоставляет клиента с политикой банка и показывает, при каких условиях
онбординг ей соответствует. Он не ищет, как обойти политику: жёсткие
запреты остаются запретами, а условия берутся только из текста самой
политики. На сцене формулировка «обойти policy» снимет проект с оценки, а
«найти соответствующий политике путь для клиента высокого риска» — это
стандартный risk-based approach.

 1. Политика. Синтетическая, 12–20 пунктов, по мотивам публичных политик
     банков для оборонного и других чувствительных секторов. Пишет Леонид,
     пересказом, без копирования чужого текста.
 2. Разметка пунктов — вручную, как данные, в первые часы. Для каждого
     пункта:
           type : hard_exclusion / conditional / discretionary ;
          условие срабатывания;

          что требуется: углублённая проверка (EDD), одобрение уровня X,
          ограничения по продуктам, мониторинг;
          цитата пункта. Двадцать пунктов размечаются руками за час; разметка
          политики моделью на сцене — лишний риск.
 3. Сопоставление. Факты клиента (результаты F1 + KYC-досье, локально) →
     сработавшие пункты, у каждого — факт, который его вызвал.
 4. Итог. Prohibited (сработал жёсткий запрет), Eligible with conditions
     (список условий из политики с цитатами), Eligible .
 5. Обоснование для риск-комитета. Черновик, локальная модель.
 6. Красные линии в коде. Жёсткий запрет или подтверждённое санкционное
     совпадение → Prohibited независимо от того, что ответила модель. Система
     никогда не предлагает переформулировать факты, скрыть информацию или
     разделить отношения, чтобы не попасть под порог.

Пример для демо: оборонный поставщик. Пункт «не финансируем компании,
производящие запрещённые виды оружия» — жёсткий запрет. Пункт
«оборонный сектор допускается при подтверждённом соблюдении
экспортного контроля, углублённой проверке и одобрении старшего уровня» —
условный. Два демо-клиента дают разные итоги: один Prohibited , второй
 Eligible with conditions .

Модели: только локальная. Политика и досье — конфиденциальны.

Готово, когда: два клиента дают разные итоги, и у каждого сработавшего
пункта видны цитата политики и факт-триггер.


F5. Ассистент аналитика и бриф для руководства
F5 собирает результаты F1–F4 в одностраничный бриф для руководства и
отвечает на вопросы аналитика только по уже собранным данным.

 1. Шаблон брифа: резюме (балл, полоса, итог по политике), ключевые факты с
    цитатами, связи, условия онбординга, открытые вопросы, дата среза данных.
 2. Генерация по секциям. Секции на публичных фактах могут идти в облако;
     секции с досье клиента и политикой — локально. Решает роутер по меткам
     данных, а не разработчик в коде фичи.
 3. Вопросы аналитика. «Почему балл 7?», «какие факты старше пяти лет?».
     Ответ только из findings и assessments , со ссылками. Вопрос вне собранных
     данных → «нет данных», без похода в интернет.
 4. Экспорт в PDF.

Аргументы «почему такой балл» — это разложение, а не текст модели: под
каждым компонентом факты, которые его дали, с цитатами, и формула по
клику. Отдельный блок «почему не выше» — что отброшено: оправдания,
одноимённые компании, перепечатки. Модель может пересказать это
человеческим языком, но число в пересказе берётся из расчёта, а не
генерируется.


AI Control Layer для трека Goldman
Для Goldman продукт — пример того, как дать ИИ доступ к клиентским данным
и к интернету, не потеряв контроль. Слой контроля должен быть виден на
экране, иначе жюри увидит просто KYC-инструмент.

     Метки данных. public / confidential / restricted на каждой записи.
     Роутер запрещает конфиденциальное в облако кодом.
     Недоверенный контент. Статьи — данные, а не инструкции. У моделей,
     которые читают статьи (Jev, извлечение фактов), нет инструментов с
     побочными эффектами: они только возвращают JSON.
     Красные линии как код. Жёсткие запреты политики и санкционное
     правило работают без LLM.
     Бюджеты. Лимит запусков Apify и вызовов LLM на одну проверку,
